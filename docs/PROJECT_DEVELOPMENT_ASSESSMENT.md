## 1. 总体结论

`super` 当前已经不是早期演示型多 Agent 看板，而是一个本地量化研究与模拟交易控制台。它覆盖了分析任务、Agent DAG、行情与持仓输入、Final Writer、SignalOps 模拟股票池、Backtest、Research Lab、Case / Knowledge / Evaluation、插件注册、配置治理、审计和生产健康观测。

当前最重要的边界是：系统仍应被定义为研究与模拟环境，不是生产级实盘自动交易系统。SignalOps 继续保持 `simulation_only=true`，所有 `SIM_*` 动作只代表沙箱模拟，不应被描述为券商自动下单能力。

SignalOps 的设计理念是高度智能自动化：默认工作流应由系统自动跟踪、判断、复盘、调参和沉淀证据，尽量减少人工日常配置和人工触发。人的职责应收敛为审查、授权、复核边界和处理高风险例外，不作为日常信号生成、模拟买卖和研究沉淀的驱动者。智能化不等于真实交易自动化；所有自动动作仍限定在沙箱模拟、Research Lab 证据链和人工可复核结论内。

当前主要短板也不再是页面数量或 API 数量，而是：

- 真实可复核样例链路仍不够饱满，很多治理模块有结构但缺长期沉淀数据。
- 配置治理已经具备审计、版本可见性、secret-safe rollback 阻断提示、Agent Runtime surface-scoped approved restore 和基础审批语义；非 Agent Runtime 外部配置面与更完整审批流仍需要专项设计。
- 后台任务已有持久镜像、状态历史和恢复能力，但仍不是外部 worker/queue 架构。
- 自动化回归覆盖以单元/API/构建为主；Research closure 浏览器 smoke 已覆盖多条主链路和 Backend Status productionHealth 可见性，但仍缺少完整浏览器 E2E 套件。
- 历史文档数量多且存在过期叙述，后续应以本评估、`DEVELOPMENT_GUIDE.md`、`QUANT_SYSTEM_IMPROVEMENT_PLAN.md` 和 `DEVELOPMENT_LOG.md` 为准。

## 5. 当前真实风险清单

SignalOps 页面和文档必须持续强调 simulation-only。任何真实交易、券商下单、账户直连都需要独立设计、独立权限、独立审计和人工确认，不属于当前默认能力。

### R2. 权限治理后端强于前端

## 6. 下一阶段路线

### P0：文档和入口校准

目标：让新开发者不会改错目录、跑错测试、误读系统边界。

- 明确 `frontend/src` 是活跃前端，根 `src/` 已删除且不应恢复。
- 统一 README、测试指南、部署文档和本开发指南里的命令。
- 清理或标注过期文档，避免旧 backlog 重新成为计划来源。
- 记录本地端口、启动方式和 API docs 入口。

### P1：权限和配置治理补齐

目标：让所有高风险写入在 UI 和后端都可解释、可审计、可禁用。

- 前端 role-aware 禁用已覆盖 SignalOps 生命周期/人工控制/签名审查事件/运行配置、Backend Status production-alert dispatch/handoff 与 ops-log handoff、Settings 数据源和行情适配器写入/检查、Data Health 主动检查、Plugin runtime checks、Portfolio/New Task/Knowledge/Data Compression/Backtest/Live Run 等研究或运行写入口、Agent Runtime profile 写入/测试、Config Versions approved restore，以及主要删除/回滚页面；后续重点是新增高风险入口的持续 guard 和统一提示。
- 外部 Agent Runtime 配置已有可执行的 surface-scoped secret-safe rollback；未来非 Agent Runtime 外部配置面需要各自 restore executor。
- 为配置发布、回滚、外部调用 allowlist 增加审批门槛和差异预览。
- 在 Config Versions 页面继续补齐非 Agent Runtime 外部配置面的恢复影响；Agent Runtime approved restore 已有审批状态、actor/filter 视图、governed modal 和 surface-scoped 后端执行器。

### P2：第一条真实样例闭环

目标：把宽功能面变成可演示、可复核、可持续学习的链路。

- 生成或维护一条样例链：portfolio -> analysis run -> SignalOps -> backtest -> Research verdict -> case -> knowledge version -> evaluation。
- 每一步都展示 ID、来源、时间戳、证据强度、缺失项和下一步建议。
- Dashboard 和 Research Lab 提供一键进入或重建样例链的入口。

### P3：研究级验证深度

目标：让结果更接近研究流程，而不是只展示一次性分析。

- Backtest 增加 benchmark、参数扫描、样本外分段、walk-forward 和实验数据包 hash。
- Knowledge version 发布后自动触发代表性 case 回归，并展示改善/退化/待复核比例。
- Technical Kline 治理纳入版本、回滚、误判 case 和样本不足判定。

### P4：生产化工程能力

目标：把当前本地控制台能力推进到可运维的服务形态。

- 外部 worker/queue、分布式任务 lease enforcement、幂等和恢复；当前已有本地 SQLite job/attempt mirror、lease metadata 和本地 worker owner guard，仍需真正外部队列。
- 浏览器 E2E 冒烟套件。
- 外部集中日志聚合/长期留存、厂商级告警规则、定期真实离机备份恢复演练；本地 structured ops log API/UI、alert outbox、generic webhook alert provider、bounded webhook retry、`smoke:db-backup-restore`、`smoke:db-offhost-backup` 和 `smoke:storage-offhost-restore` 已覆盖本地可观测与脚本级演练。
- 插件执行沙箱专项设计，默认继续禁止任意代码和真实交易动作；archive、governed upgrade、package artifact migration metadata、真实 artifact storage/upload/hash verification、local SHA-256 denylist scan、metadata-only zip path scan、retention metadata、admin-gated local retention cleanup/dry-run、runtime resource quota 可见化、audit-derived usage stats 和按日 usage history 已具备，生产级 object-storage lifecycle、外部/厂商级恶意软件扫描和威胁情报 feed 仍需后续设计。

## 7. 开发决策原则

- 先修阻断主链路的真实问题，再做横向能力扩展。
- 任何 API schema 变化必须同步前端类型和调用方。
- 任何配置、auth、cookie、session、operator、token、secret 改动必须补测试。
- 任何 SignalOps 交易语义改动必须保持 simulation-only，并覆盖 A 股规则边界。
- SignalOps 新功能优先自动化工作流；人工入口只用于审查、配置边界、强制沙箱控制和异常处置，不得把人工手工维护重新变成主路径。
- 任何 Final Writer 或结论展示改动都不能绕过 DVG、Risk、QIAM 和 Execution 门禁。
- 文档更新必须基于当前源码和验证结果，不从已删除的旧 backlog 直接复制未复核条目。
